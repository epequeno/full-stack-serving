# 0011 — Serve Qwen2.5-1.5B-Instruct in bf16, unquantized

- **Status:** accepted
- **Date:** 2026-10-10

## Context

Full-stack-serving ADR 0002 fixed the *criteria* for the model and deferred the concrete choice
to the host inventory, which is now committed (`results/l0-local/host-inventory.md`, 2026-10-10):
one NVIDIA RTX 4070 Ti SUPER, **16 376 MiB** (15.99 GiB), compute capability 8.9, GeForce — so
**no MIG**. The inventory's ceilings (FP16 ~6B, FP8/INT8 ~13B, 4-bit ~26B params) are before KV
cache and activations, so they only bound the search.

Two numbers drive everything else:

- **The workload** is fixed by the committed fixtures: ~843-word prompts (word salad, which
  tokenizes worse than prose), `max_tokens: 128`, closed-loop concurrency up to **64**
  (full-stack-serving ADR 0004). ADR 0002 criterion 1 adds that **two replicas** must fit,
  because L2's routing and L3's autoscaling are meaningless with one backend.
- **KV cost per token is an architecture property, computable exactly from the published
  configs**: `layers × 2 (K+V) × kv_heads × head_dim × bytes`. On a 16 GB card it — not weight
  size — is what separates the candidates.

Sources read 2026-10-10: the HF model API and `config.json` of each candidate below, and the
Qwen2.5-1.5B safetensors metadata (1 543 714 304 parameters, all BF16, `license: apache-2.0`,
ungated; repo revision `989aa7980e4cf806f80c7fef2b1adb7bc71aa306`).

## Decision

Serve **`Qwen/Qwen2.5-1.5B-Instruct`** (`Qwen2ForCausalLM`) in **bf16, exactly as published —
no quantization, no dtype conversion.** Pin the HF revision in `stack/l0-local/`.

The fit against ADR 0002's criteria, worst cell = 64 requests × a 1.5K-token planning bound
(prompt + template + 128 output; the true count is measured at L0 from the server's `usage` —
the fixtures README's "Not verified" item):

| quantity | value | from |
|---|---|---|
| weights | 1 543 714 304 × 2 B ≈ **2.9 GiB** | HF safetensors |
| KV per token | 28 × 2 × 2 × 128 × 2 = 28 672 B ≈ **28 KiB** | `config.json` |
| KV, worst cell (≤98K tokens) | ≈ **2.6 GiB** | computed |
| **two replicas** | 2 × (2.9 + 2.6) ≈ **11 GiB** < 15.99 GiB, ≈5 GiB headroom for activations and engine overhead | computed |

Criterion 2 holds structurally (2.9 GiB of weights on 1.7 TB of local NVMe); the actual cold-start
number is an L0 result, not asserted here.

**Criterion 3 is a check, not an assumption.** At batch 1, decode re-reads the weights each step:
2.9 GiB at the card's ~0.67 TB/s is ≈4 ms/token — comfortably above the sub-millisecond
client-side event cost, unlike the 0.5B class (below). These are estimates; the
harness-overhead measurement `measure/README.md` already requires decides, with and without the
per-chunk `usage` option (ADR 0005). If GPU time does not dominate, this ADR is superseded — the
model changes, it is not excused (ADR 0002).

**Criterion 5 is verified at L0 bring-up** against the pinned vLLM version: Qwen2 architecture
support, automatic prefix caching, and the metrics endpoint, plus the fixtures' token-length
check against the 32 768-token context window. The engine itself is vLLM by L0 working
assumption and gets its own ADR.

Why the alternatives fail one of ADR 0002's criteria:

- **Qwen3-1.7B** (also Apache-2.0, ungated — the otherwise-natural newer pick): 28 layers ×
  **8** KV heads × 128 head dim = 114 688 B ≈ **112 KiB/token — 4× this model's KV**. The same
  worst cell needs ≈10.5 GiB of KV; two replicas cannot fit and even one leaves no headroom
  (criterion 1). Its hybrid thinking mode is also a chat-template switch the levels don't need.
- **Qwen2.5-3B**: ≈5.8 GiB weights × 2 + 36 KiB/token KV (36 layers) ≈ 18 GiB per pair — over
  the card (criterion 1).
- **Qwen2.5-0.5B / Qwen3-0.6B**: ~1 GiB weights → ≈1.5 ms/token at batch 1, the same order as
  client/HTTP overhead — criterion 3 at risk from the start, and ADR 0002 forbids excusing it.
- **Llama-3.2-1B**: gated access (manual review, personal details, token) — criterion 4 fails
  outright.
- **Any quantization** (fp8/int8/AWQ): unnecessary for fit, inserts a kernel path between the
  measurement and the model, and shrinks per-token GPU time toward harness noise. Rejected by
  ADR 0002's easy-to-observe-over-impressive rule.

## Consequences

- The model is a pinned, interchangeable parameter in `stack/l0-local/`; swapping it touches no
  `loadgen/` or `measure/` code (ADR 0002).
- Two replicas fit only at this scale. The *mechanics* of two replicas on one non-MIG GPU (two
  engine processes with split `gpu_memory_utilization`, time-sliced) are the L2/L3 ADR's to
  decide; the fit table above is what they start from.
- Absolute numbers do not transfer (ADR 0002); every results page states the model. Cold start
  and scale-up latency are optimistic and reported with the model's size.
- The L2 shared-prefix fixture fits the prefix cache trivially at 28 KiB/token, so a measured
  hit rate reads against the fixtures' 87.5% ceiling without cache-capacity confounds.
- If criterion 3 fails at L0, the successor ADR faces the real trade-off: every larger
  candidate above breaks criterion 1, so the honest moves are fewer replicas or different
  hardware — not a bigger model quietly excused.
