# 0010 — Run L1 on k3s

- **Status:** accepted
- **Date:** 2026-10-09

## Context

L1 puts the serving workload on a single-node Kubernetes cluster with the GPU visible to pods. The
choice of distribution decides how hard the GPU path is, and it shapes what L1's comparison with L0
can claim.

**What was read (2026-10-09):**

- **k3s** (`docs.k3s.io/advanced`): k3s detects alternative container runtimes at startup,
  including `nvidia`, `nvidia-cdi` and `nvidia-experimental`, and adds them to its containerd
  configuration when the executables are found. The documented check is
  `grep nvidia /var/lib/rancher/k3s/agent/etc/containerd/config.toml`. Unless the default runtime
  is changed, pods must set `runtimeClassName: nvidia`. The page says the NVIDIA Container Runtime
  "is also frequently used with NVIDIA Device Plugin", so the device plugin is a separate
  install.
- **kind** (`kubernetes-sigs/kind`): "Support GPUs" (#3164) and "Proposal: Lightweight
  cross-provider GPU support" (#4122) are both **open**. The quick-start and known-issues pages
  mention neither GPUs nor NVIDIA. Three older issues ("Add GPU support", "add gpus support in
  docker provider", "Add API for CDI --devices flag…") are closed, but **the reason for closing
  was not read**, so this does not show GPU support exists or doesn't. Community workarounds
  may exist and were not examined.

**Not examined:** minikube, MicroK8s, RKE2, kubeadm. No claim is made about them.

## Decision

Use **k3s** for L1, on the Linux GPU host.

- It has a documented NVIDIA path in its own docs, which kind does not, as far as was found.
- kind runs nodes as containers, so a GPU has to be passed into the node container, and the
  project's own tracker lists that as open. L1's evidence depends on the GPU path being boring.
- A single node needs no VM layer on the GPU host.

The NVIDIA device plugin vs GPU Operator question is **not decided here**.

## Consequences

- **L1 vs L0 is not "Kubernetes overhead".** L0 runs under Docker; L1 runs under k3s's containerd,
  with a CNI, kube-proxy and Service networking in the path. The difference between them
  includes all of that. The L1 finding is worded **"Kubernetes deployment vs Docker
  deployment"**, never "Kubernetes overhead". Where the load generator runs (host or pod) and the
  network path (hostNetwork, NodePort, ClusterIP) are recorded in `env`. An arm that separates the network
  path from the runtime is possible and is **not decided here**.
- **Two image stores.** Docker and k3s's containerd do not share images, so the engine image is
  pulled twice, and weights are fetched separately unless a shared host path is mounted.
  `make inventory` reports free disk for this reason.
- **One GPU, one owner at a time.** L0's container and L1's pod cannot both hold the GPU. `make
  down` for one level must precede `make up` for the next.
- **Linux only.** L1 cannot run on the development Mac. It exists only on the GPU host.
- The `nvidia` runtime appearing in k3s's containerd config is the first thing to verify at L1,
  with the grep above, before debugging anything else.
- If L1 shows the GPU path is not boring on this host, this ADR is wrong in practice and gets
  superseded, not patched.
